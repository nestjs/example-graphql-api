## Production data: NestJS Observe

This app reports its traces, errors, logs and metrics to [NestJS Observe](https://observe.nestjs.com) through `ObserveModule`, registered first in `src/app.module.ts` (and `instrument: ObserveInstrument` in `src/main.ts`). Its key pair comes from `OBSERVE_APP_KEY` and `OBSERVE_APP_SECRET` in `.env`, which `npx @nestjs/observe link` writes.

When a task depends on how the app behaves in production - an error users hit, a slow endpoint, a failing job, whether a release made things worse - work from that data, not from the code alone:

- The Observe MCP server answers those questions directly: errors with their traces and logs, slow operations, jobs, and what a release changed (`find_regressions`, `diff_release`). It is included on the Pro plan and above. In Claude Code: `claude mcp add observe --transport http https://observe-api.nestjs.com/mcp`, and the client opens a browser to approve. Other clients: https://www.observe.nestjs.com/documentation/mcp
- Without it, the user can open the request or error in the Observe dashboard and click **Copy agent prompt**, which hands over that page's trace, stack and logs as text.

## This project

A GraphQL API for a blog, code first, on Apollo Server and the Node adapter: posts with drafts, comments, cursor pagination, batched nested fields, sign-in mutations with rotating refresh tokens, and comment subscriptions over `graphql-ws`, on PostgreSQL through Drizzle. It is the finished app of https://docs.nestjs.com/tutorials/graphql-api, which explains each part; keep the code in step with that page.

- Layout: one folder per feature under `src/` (`posts/`, `users/`, `auth/`), each with its models (`*.model.ts`), inputs and args (`*.inputs.ts`), resolvers and a module. `src/graphql/` holds what every operation shares: the module's options and the WebSocket checks (`graphql.config.ts`) and the error helpers (`errors.ts`). `src/app.module.ts` registers everything; `ObserveModule.forRoot()` stays first in its imports, and `src/main.ts` passes `instrument: ObserveInstrument`. `nest generate` (for example `nest g resolver tags`) writes files under `src/` and registers them in the closest `*.module.ts`; pass `--no-spec`, since this project's tests are the e2e files in `test/`.
- The environment is the Zod schema in `src/config.ts`, checked at startup: add a variable there, and to `.env.example`. The Observe keys are the exception: `ObserveModule.forRoot()` reads `OBSERVE_APP_KEY` and `OBSERVE_APP_SECRET` from `process.env` directly.
- Validation: class-validator decorators on the `@ArgsType()` and `@InputType()` classes, through the global `ValidationPipe`, whose `exceptionFactory` (`badUserInput()` in `src/graphql/errors.ts`) turns failures into `BAD_USER_INPUT` with the messages by field. An optional field that maps to a `NOT NULL` column uses `ifSent` (`ValidateIf` on `!== undefined`), never `@IsOptional()`, which lets `null` through. List sizes are `first`, between 1 and 50.
- Errors: throw a `GraphQLError` with an `extensions.code` (or `notFound()`), or a Nest exception such as `ForbiddenException`, which becomes `FORBIDDEN`. `GraphQLErrorFilter` passes `GraphQLError`s on; in production `formatError` replaces any `INTERNAL_SERVER_ERROR` with a bare `Internal server error`. Someone else's draft is `null` (or `NOT_FOUND`), exactly like an unknown id, never `FORBIDDEN`, which would confirm it exists: a write that matches nothing is `FORBIDDEN` only for a post the user may see (`PostsService.refuse()`).
- Auth: `@nestjs/authentication`'s global guard requires a user on every operation unless it says otherwise. The resolvers of `posts/` and `users/` are `@Authenticate({ optional: true })` at class level, so anyone may read and `@CurrentUser()` still gets a signed-in viewer; their mutations, `me` and `commentAdded` set `@Authenticate({ optional: false })`. Only `AuthResolver` is `@Public()`, and only it has `GqlThrottlerGuard` (with `fieldResolverEnhancers`, a global throttler guard would count every field). Field resolvers run guards, interceptors and filters too, so they get `@CurrentUser()` for their own operation: decide per-user fields (like `User.email`) there, not in field middleware. Only `UsersRepository.findCredentials()` returns a password hash, to `CredentialsService`; every other read of users leaves the column out (`findById()`, `UsersLoader`).
- Drafts: every query that reads posts for a viewer goes through `visibleTo(viewerId)` in `src/posts/visibility.ts` (`PostsService.findVisible()`, which `post`, the write checks and `commentAdded` use, and `PostsLoader`); the `posts` list reads published posts only. A new path to posts must do the same.
- Nested fields load through one request-scoped DataLoader per table, in its feature folder: `UsersLoader` (`users/`), `PostsLoader` and `CommentsLoader` (`posts/`), never with a query per parent. A new field adds a method to the loader of the table it reads. One instance per operation; a subscription keeps its instances for every event, hence `cache: false`. Resolvers that inject a loader become request-scoped; a resolver with `@Subscription()` must stay a singleton, which is why `Comment.author` lives in `CommentAuthorResolver`. `PostsModule` imports `UsersModule`, never the reverse: `User.posts` is resolved in `posts/user-posts.resolver.ts`.
- The WebSocket: `graphql-ws` runs operations outside Apollo Server and its plugins, so `graphql.config.ts` authenticates the socket once in `onConnect` (token from `connectionParams.authorization`, 4403 otherwise) and, in `onSubscribe`, validates each operation and allows subscriptions only (no introspection, queries or mutations over the socket). Keep both when changing subscriptions. `PubSub` is in memory: one topic per post, one instance only.
- `updatePost` and `publishPost` are single conditional statements (`UPDATE ... WHERE` on the id and the author), not read-then-save; when nothing matched, `refuse()` works out the error.
- Migrations: change `src/database/schema.ts`, run `npm run db:generate`, and commit the folder it writes in `drizzle/`. `npm run db:migrate` applies them. `npm run db:seed` runs the built `dist/database/seed.js` (build first) and empties the tables: development only, it refuses `NODE_ENV=production`.
- Tests: `TEST_DATABASE_URL=postgres://postgres:blog@localhost:5432/blog_test TEST_PORT=3001 npm run test:e2e`; without `TEST_DATABASE_URL` they are skipped. They boot the real `AppModule` on that database (truncated first, one file at a time), count the SQL statements it sends, and the WebSocket tests listen on 127.0.0.1 at `TEST_PORT`. `test/blog.e2e-spec.ts` protects draft visibility on every path, a flat SQL count as posts grow (DataLoader), and the socket refusing a missing or invalid token. `test/errors.e2e-spec.ts` protects `UNAUTHENTICATED` and `FORBIDDEN`, email visibility, `BAD_USER_INPUT` messages, and refresh-token rotation and reuse. `test/subscriptions.e2e-spec.ts` protects per-post delivery, another user's draft as `NOT_FOUND`, and the socket refusing introspection and mutations. `test/production.e2e-spec.ts` protects error masking with `NODE_ENV=production`.
- `vitest.config.e2e.ts` aliases `graphql` to its CommonJS build: without it, the tests load a second copy of `graphql` and the schema is rejected. Keep it.

This project is ESM: relative imports end in `.js`, and `__dirname` doesn't exist (use `import.meta.dirname`).
